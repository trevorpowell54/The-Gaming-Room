# The-Gaming-Room

# The Gaming Room Portfolio Reflection

### 1. Briefly summarize The Gaming Room client and their software requirements.

The Gaming Room was a client that wanted to expand their existing Android-based game, *Draw It or Lose It*, into a web-based application that could support multiple platforms. The client needed a software design that would allow users to participate in a multiplayer drawing game while maintaining reliable game management and data integrity. The application needed to support multiple teams and players, ensure that game and player names were unique, and provide a structure that could scale as the application grew. The design also required consideration of operating systems, architecture, storage, security, and development requirements.

### 2. What did you do particularly well in developing this documentation?

I did particularly well at organizing the software requirements and translating them into a structured software design. I considered important areas such as the application's architecture, operating system requirements, memory management, storage, security, and scalability. I also used UML diagrams to show the relationships between the different components of the application. This helped make the design easier for both the client and development team to understand. Another strength was connecting the client's requirements to specific technical decisions instead of simply describing the application at a high level.

### 3. What about the process of working through a design document did you find helpful when developing the code?

The design document provided a roadmap for developing the application. Working through the requirements and UML diagrams before writing code helped me understand how the classes and components needed to interact. It also helped identify responsibilities for objects such as games, teams, and players before implementation began. Having the design documented made it easier to reference the intended structure while coding and reduced the need to make major architectural decisions during development. This experience showed me that planning before implementation can make the coding process more organized and efficient.

### 4. If you could choose one part of your work on these documents to revise, what would you pick? How would you improve it?

If I could revise one part of the documentation, I would improve the explanation of the application's architecture and how the different components communicate with one another. I would provide more detailed descriptions of the flow of information between the client, application components, and data layer. I would also make the diagrams more detailed where appropriate so that a developer could use them as a stronger reference during implementation. This would make the document even more useful as a development resource rather than primarily serving as a design overview.

### 5. How did you interpret the user's needs and implement them into your software design? Why is it so important to consider the user's needs when designing?

I interpreted the user's needs by focusing on the functionality the client expected from the game and translating those requirements into technical specifications. The design needed to support multiplayer gameplay, maintain unique game and player information, and provide an application structure that could operate reliably across platforms. I considered both the immediate requirements and potential future needs such as scalability and maintainability.

Considering user needs is important because software is ultimately designed to solve problems for its users. A technically sophisticated application can still be unsuccessful if it does not provide the functionality or experience the user expects. Understanding requirements before development helps ensure that the final product addresses the actual problem and reduces the possibility of expensive changes later in the development process.

### 6. How did you approach designing software? What techniques or strategies would you use in the future to analyze and design a similar software application?

I approached software design by first identifying the client's requirements and then breaking those requirements into smaller technical components. I considered the application's architecture, objects, relationships, operating environment, security, and scalability. UML diagrams were particularly useful because they allowed me to visualize relationships between classes before implementing them in code.

In the future, I would continue using a requirements-first approach. I would begin by identifying functional and nonfunctional requirements, create use cases and UML diagrams, identify the major classes and their responsibilities, and evaluate architectural options before coding. I would also consider security, scalability, maintainability, and testing earlier in the design process. This approach would provide a clear foundation for development and make it easier to ensure that the completed application meets both technical requirements and user expectations.
